# Сервисный центр

Учебное консольное приложение на Java для учёта клиентов и заявок на ремонт.
Вторая аттестация: хранение клиентов и заявок в PostgreSQL через JDBC.
Данные сохраняются между запусками приложения.

- `task1` — первая аттестация: предметная модель, хранение в памяти и CLI.
- `task2` — вторая аттестация: PostgreSQL и JDBC, тот же консольный интерфейс.

## Требования

- JDK 21. Проверить установленную версию можно командой `java -version`.
- Git для клонирования репозитория.
- PostgreSQL для запуска приложения. Использовал PostgreSQL 18 на macOS.
- Доступ к интернету при первой сборке для загрузки Gradle и зависимостей.

DBeaver можно использовать для создания базы, выполнения SQL и просмотра данных;
для работы самого Java-приложения он не требуется.

В `build.gradle` закреплена Java 21 через toolchain: Gradle использует JDK 21
для компиляции, тестов и запуска приложения. JDK 21 нужно установить заранее.

Gradle отдельно устанавливать не нужно: в репозитории есть Gradle Wrapper,
который загружает версию 9.6.0. IDEA и Docker для запуска не нужны.
Если установлено несколько JDK, укажите JDK 21 в `JAVA_HOME` и убедитесь, что
`java` доступна в `PATH`.

## Клонирование и сборка

Клонируйте ветку второй аттестации:

```bash
git clone --branch task2 https://github.com/exzoe/service-center.git
cd service-center
```

На macOS и Linux выполните:

```bash
./gradlew clean build
```

На Windows в PowerShell:

```powershell
.\gradlew.bat clean build
```

Команда компилирует проект, запускает тесты и создаёт артефакты сборки в `build/`.
Ожидаемый результат успешной сборки — `BUILD SUCCESSFUL`.
При первом запуске загрузка Gradle и зависимостей может занять время.
Для сборки и автоматических тестов запущенная БД не нужна: тесты сервисов
используют репозитории в памяти. Для запуска приложения подготовьте PostgreSQL
по инструкции ниже.

## Подготовка базы данных

1. Запустите PostgreSQL и создайте базу:

```sql
CREATE DATABASE service_center;
```

2. В базе `service_center` выполните `src/main/resources/schema.sql`.
   Схема применяется один раз; автоматически таблицы не создаются.
3. Укажите параметры подключения в `src/main/resources/database.properties`:

```properties
db.url=jdbc:postgresql://localhost:5432/service_center
db.user=home
db.password=
```

Замените пользователя и пароль на свои; при необходимости измените адрес и порт.

## Запуск

Перед запуском PostgreSQL должен работать, таблицы должны быть созданы,
а настройки подключения — соответствовать вашей установке.

На macOS и Linux:

```bash
./gradlew --console=plain run
```

На Windows в PowerShell:

```powershell
.\gradlew.bat --console=plain run
```

Введите текстовую команду из меню, например `client-add` или `order-list`.
Для завершения работы введите `exit`.

Клиенты, заявки и изменения статусов сохраняются в PostgreSQL. После выхода
из Java-приложения данные остаются в базе. DBeaver при этом можно закрыть.

Если подключение не удалось, проверьте запуск сервера, адрес и порт, пользователя
и пароль. При ошибке отсутствующей таблицы проверьте, что `schema.sql` выполнен
именно в `service_center`. Ошибки JDBC сейчас оборачиваются в
`IllegalStateException`; приложение может завершиться с текстом ошибки
и исходной причиной в стеке вызовов.

## Windows: кодировка

Сборку и работу с PostgreSQL проверял на macOS с JDK 21. Первую часть также
проверял из свежего клона; вторую пока запускал только в рабочей папке проекта.

На Windows 10 при проверке первой части возникали проблемы с кириллицей
в консоли. Работу текущей версии на Windows с JDK 21 пока не проверял.
Для запуска нужен JDK 21. При проблемах с кодировкой можно попробовать
Windows Terminal и UTF-8:

```powershell
chcp 65001
.\gradlew.bat --stop
.\gradlew.bat clean build
.\gradlew.bat --console=plain run
```

Кодировка исходников в Gradle задана как UTF-8. После запуска проверьте
отображение меню и ввод русского имени клиента.

## Возможности

| Команда | Действие |
| --- | --- |
| `client-add` | Добавить клиента: имя и телефон |
| `client-list` | Показать клиентов и их ID |
| `order-create` | Создать заявку для существующего клиента |
| `order-list` | Показать все заявки |
| `order-status` | Изменить статус заявки |
| `order-update` | Изменить устройство и описание неисправности |
| `order-delete` | Удалить новую заявку |
| `order-find` | Найти заявки по статусу |
| `exit` | Выйти |

При выборе статуса приложение показывает нумерованный список: вводится номер,
а не название константы. Идентификаторы клиентов и заявок назначает PostgreSQL
через `GENERATED ALWAYS AS IDENTITY`. После удаления записей ID не используются
повторно; пропуски в нумерации допустимы.
Для создания заявки нужно указать ID уже добавленного клиента.
Ошибки ввода и запрещённые действия отображаются сообщением в консоли.

## Правила работы с заявками

Новая заявка получает статус `NEW`. Разрешённые переходы:

| Текущий статус | Допустимый следующий статус |
| --- | --- |
| `NEW` — принята | `DIAGNOSTICS`, `CANCELLED` |
| `DIAGNOSTICS` — диагностика | `IN_REPAIR`, `CANCELLED` |
| `IN_REPAIR` — ремонт | `READY` |
| `READY` — готова к выдаче | `CLOSED` |
| `CLOSED` — выдана | Переходов нет |
| `CANCELLED` — отменена | Переходов нет |

Повторное назначение того же статуса также запрещено.
Редактировать устройство и описание или удалять заявку можно только в статусе
`NEW`. Имя клиента, телефон, устройство и описание неисправности не должны быть
пустыми или состоять только из пробелов. Формат телефонного номера отдельно
не проверяется.

## Пример работы

1. Добавьте клиента командой `client-add` и запомните выведенный ID.
2. Командой `order-create` создайте заявку для этого клиента.
3. Выполните `order-list`, чтобы увидеть заявку и её ID.
4. Пока заявка новая, при необходимости исправьте данные командой `order-update`.
5. Командой `order-status` проведите заявку по цепочке
   `NEW → DIAGNOSTICS → IN_REPAIR → READY → CLOSED`.
6. Используйте `order-find` для поиска заявок с нужным статусом.
7. Выйдите командой `exit`, запустите приложение заново и проверьте, что
   клиенты, заявки и их статусы сохранились.

## Тесты

На macOS и Linux:

```bash
./gradlew test
```

На Windows в PowerShell:

```powershell
.\gradlew.bat test
```

Тесты написаны на JUnit Jupiter. Каждый сценарий разделён на подготовку
данных (`given`), вызов проверяемой операции (`when`) и проверки (`then`):

- `ClientServiceTest`: выдача разных ID клиентам и сохранение обоих клиентов.
- `RepairOrderServiceTest`: создание и удаление заявок, полный цикл ремонта,
  отмена новой заявки, запрет недопустимого перехода статуса,
  редактирование новой заявки и запрет редактирования или удаления после начала
  диагностики. Отдельные тесты проверяют отказ в создании заявки с пустым
  описанием и сохранение данных при попытке записать пустое описание.
  Поведение приложения проверяется через сервисы.

Автоматические тесты используют `InMemoryClientRepository` и
`InMemoryRepairOrderRepository`, поэтому проверяют бизнес-логику без PostgreSQL.
Работу JDBC проверял вручную: создание, чтение, изменение и удаление записей,
а также сохранение данных после перезапуска приложения.

HTML-отчёт после выполнения тестов: `build/reports/tests/test/index.html`.

## Структура проекта

- `domain` — клиент, заявка и перечисление статусов. Сущности хранят данные;
  проверки входных данных и бизнес-правила выполняются сервисами.
- `validation` — общий `InputValidator` для проверки имени и телефона клиента,
  устройства и описания заявки. Сервисы вызывают проверки до создания
  или изменения сущностей. Данные новой заявки проверяются до выделения ID.
- `exception` — общее `AppException` с кодом причины `ErrorCode`:
  `VALIDATION` (неверные данные), `NOT_FOUND` (запись не найдена),
  `BUSINESS_RULE` (запрещённая операция). UI выводит сообщение исключения.
- `repository` — интерфейсы доступа к данным.
- `repository.jdbc` — реализации для PostgreSQL: SQL-запросы, параметры через
  `PreparedStatement`, чтение результатов и создание объектов предметной модели.
  Заявки читаются вместе с клиентами через `JOIN`. Метод `create` добавляет запись
  и возвращает объект с ID от БД; `update` изменяет существующую запись.
  Соединения и результаты запросов закрываются через `try-with-resources`.
- `repository.memory` — хранение в `HashMap`, сохранённое для тестов сервисов.
- `id` — `IdProvider` для репозиториев в памяти. У каждого репозитория свой
  экземпляр счётчика. В основном запуске ID назначает PostgreSQL.
- `config` — `ConnectionProvider`: чтение `database.properties` и открытие
  соединений через JDBC `DriverManager`. Каждый вызов `getConnection()` открывает
  новое соединение.
- `service` — создание, поиск и обработка данных с использованием репозиториев;
  правила смены статуса, редактирования и удаления заявки. Эти операции
  приложение выполняет через `RepairOrderService`.
- `ui` — цикл меню (`ConsoleUI`) и общий ввод/вывод (`ConsoleHelper`).
- `ui.command` — интерфейс `Command` с методом `execute()` и отдельный класс
  для каждого из восьми действий меню. `ConsoleUI` хранит текстовые обозначения,
  описания и команды в `LinkedHashMap`, формирует из них меню в порядке регистрации
  и вызывает `execute()` выбранной команды. Все команды используют общий
  `ConsoleHelper` с одним `Scanner`. Ошибки обрабатываются в цикле меню;
  цикл работает, пока `running` равен `true`. Команда `exit` или окончание
  ввода сбрасывает этот флаг и завершает цикл.
- `factory` — фабрики сборки приложения:
  `ServiceFactory` создаёт общий `ConnectionProvider`, JDBC-репозитории и сервисы;
  `ConsoleUIFactory` создаёт общий ввод, консольный интерфейс и регистрирует команды;
  `ApplicationFactory` связывает результаты этих фабрик.
- `Main` — вывод заголовка и запуск приложения через `ApplicationFactory.create().run()`.
- `src/test/java` — автоматические тесты.
- `src/main/resources/schema.sql` — SQL для первоначального создания таблиц.
- `src/main/resources/database.properties` — настройки подключения к PostgreSQL.

## Хранение и дальнейшее развитие

Основное приложение использует PostgreSQL через JDBC. Связь заявки с клиентом
защищена внешним ключом: нельзя добавить заявку для отсутствующего клиента
или удалить клиента, на которого ссылаются заявки. Статус хранится строкой,
а допустимые переходы и ограничения редактирования проверяет Java-сервис.

Веб-интерфейс на сервлетах планируется для третьей аттестации и пока не реализован.
